## 1. 亮点分级

同一批工作，价值并不相同。按下表分三级投入时间：**主攻项必须有数据，加分项不预留工期，降级项不进主线。**

| 编号 | 亮点 | 所在层 | 定位 | 依据 |
|---|---|---|---|---|
| **③** | 端侧推理落地 | L0 | **主攻 · 优先级最高** | 20KB RAM 的 M3 上部署量化模型，是"具身智能"这个词唯一能落地的实证；目前尚无任何实测数据 |
| **①** | 无传感器力估计（电流即触觉） | L0 | **主攻** | 不增加传感器、用执行器自身反推外力，是可量化、可复现的力控入口 |
| **②** | 慢脑 - 快反射（时间契约 + 降级） | L0–L2 | **主攻** | 把"AI 不实时"从缺陷变成架构约束，是全项目唯一不可被单点替换的设计 |
| **④** | 隐私在场感知（雷达替代摄像头） | L1 | 加分 | 叙事强，但 LD2410 是黑盒模块，技术深度依赖系统集成而非算法 |
| ➕ | 主动干预的打扰成本建模 | L2 | 加分 · 后置 | 有 A/B 数据才成立；否则退化成"阈值 + 规则"，证明不了工程能力 |
| — | 记忆系统（遗忘曲线） | L2 | 降级 | 对四项核心能力贡献低，实现上容易退化成"数据库 + 排序" |

分级依据只有两条：**技术密度**（别人难以复制）与 **可验证性**（能落成一个数字）。两项都低的功能，写得再好也只是叙述。

## 2. 能力对齐

同一批能力在两套系统中都能对应到真实问题。下表左半是能力的行业含义，右半是本项目能给出的证据。

| 能力项 | 机器人 / 运动控制 | 储能 BMS / 汽车电子 | 本项目证据 | 现状 |
|---|---|---|---|---|
| 电流采样与信号链 | 无传感器力矩估计、触觉分级 | 高边 / 低边电流检测、过流保护 | 0.1Ω 采样 + 差分放大 + 10kHz ADC/DMA | 计划 · P1 |
| 实时控制环 | 1kHz 舵机环、阻抗控制雏形 | 保护动作时间、任务调度、WCET | 定时器节拍 + DWT 打点 + P95/抖动 | 计划 · P1 |
| 通信协议与降级 | 上下位机协议、心跳 | 类 CAN / Modbus 帧结构、异常处理 | CRC8 定长帧 + 心跳超时降级 | 帧层已实现，心跳 P2 |
| 端侧推理 | 边缘感知 | 边缘诊断（SOH 趋势、异常检测） | int8 1D-CNN + arena 复用 + 定点 requantize | **无实测数据** |
| 故障与安全 | 故障注入、断连存活 | 多级故障保护、看门狗、失效安全 | 6 类故障注入矩阵 | 计划 · P2 |

表中唯一空着的是**端侧推理**。它也是四项核心能力里唯一没有一行代码支撑的一项，因此排在第 4 节首位。

## 3. 术语约定

同一个对象在全库使用同一个名字，且名字反映结构而非感受。

| 术语 | 定义 | 不采用的写法 |
|---|---|---|
| **状态槽** | L0 内唯一的共享状态向量（4 维，取值 0~1）。L2 只能写目标值，不能直接控制执行器 | "情绪状态槽"——会被读成 UI 动效参数 |
| **行为仲裁** | 单一状态源 + 固定优先级仲裁器，驱动 4 类异构执行器（显示 / 舵机 / 灯 / 语音） | "4 维情绪驱动表情" |
| **能力词** | `sensorless force estimation` · `on-device inference` · `real-time contract with graceful degradation` | 以场景词（"陪伴""桌面玩伴"）充当技术标签 |

表述顺序固定为**先能力、后场景**。同一批代码换行业语境时只换应用背景，指标与细节必须完全一致。

## 4. 亮点 ③：端侧推理落地

### 4.1 问题

L0 侧目前没有任何模型，"端侧 AI"只存在于规划里。这是四项核心能力中唯一无法用现有代码说明的一项。

### 4.2 做法

在 **STM32F103C8T6（Cortex-M3 @72MHz，64KB Flash / 20KB SRAM，无 FPU、无 DSP 扩展）** 上，
把电流波形分类从决策树升级为 **int8 定点量化 1D-CNN**，做三方对比：

| 方案 | 体积 | 单次推理 | 准确率 | 说明 |
|---|---|---|---|---|
| 手工特征 + 阈值 | < 0.5KB | < 50µs | 基线 | 无学习能力 |
| 决策树 | ~1KB | < 100µs | 基线 | P1 先跑这个 |
| int8 1D-CNN | ~4KB | 待实测 | 目标 ≥ 85% | 本节内容 |

网络规模控制在 **5k 级 MACs**：Conv1D 1→8 k5 s2 → Conv1D 8→8 k3 s2 → FC → 4 类，约 264 参数；
输入为每 20ms 一个周期的 200 点（10kHz）双通道波形。

### 4.3 工程量在部署，不在训练

| 难点 | 具体问题 | 解法 |
|---|---|---|
| 内存 | 20KB RAM 里已有 1KB 帧缓冲、200 点双缓冲、协议栈 | 单一 arena 复用中间张量，不按层分配；用 `.map` 算出峰值 |
| 算子 | M3 无 DSP 扩展，int8 卷积无硬件加速 | 用 CMSIS-NN，说清它如何用 `__SMLAD` 一次完成两个 MAC |
| 重缩放 | 每层输出需 requantize：`(acc * M) >> shift`，M 为定点 | 说明 float 缩放系数为何不可用（软浮点开销 + 不确定性） |
| 时序 | 推理必须让出 1kHz 环 | 分片推理：一个控制周期算一层，20ms 内摊完；或降频到 50Hz 独立任务 |

### 4.4 跨平台对比

P2 引入 ESP32-S3（Xtensa，带 DSP / 向量扩展）后，同一模型跑两个平台：

> M3 无 DSP 与 S3 有 DSP，同一 int8 模型的推理耗时差多少？为省 1ms 换芯片是否值得？

这是端侧选型的真实问题，且两块板都在手上，数据可直接获得。

### 4.5 验证项

- [ ] 三方案在同一测试集（≥500 样本，4 类）上的准确率与混淆矩阵
- [ ] Flash 与 RAM 实测占用（`.map` 文件，不用估算值）
- [ ] 单次推理周期数（DWT 打点，换算 µs）
- [ ] 峰值 RAM 与 1kHz 环的最坏执行时间（WCET 粗测）
- [ ] 跨平台对比表（P2）

### 4.6 立论标准

"在 MCU 上跑了神经网络"本身不构成亮点。能说明**"为塞进 20KB 把中间张量复用到 X KB、把 float 缩放换成定点移位、把推理切成 N 片塞进 20ms 周期"**，才构成工程量。
这一节也是整个项目最容易被追问的部分，因此必须真做，不能只写方案。

## 5. 亮点 ①：从"力分类"到"力闭环"

### 5.1 问题

只识别 4 类状态 + 堵转卸力，属于**感知**，不是**控制**。闭环才是力控能力的分界。

### 5.2 三级递进

三级独立成篇，任一级完成即可交付，不必等下一级。

**D1 · 在线基线自校准（P1 内）**

SG90 的空载电流随角度、电压、温升漂移，固定阈值必然误触发。

- 滑动窗口中位数估计基线 `I0`，仅在"判定为自由运动"时更新
- 迟滞带（hysteresis）抑制阈值附近的抖动
- 记录 30 分钟连续运行的基线漂移曲线

**D2 · 导纳控制雏形（P1 末，价值最高）**

```
τ̂   = Kt · (I − I0)              # 无传感器力矩估计
Δθ  = τ̂ / K_virtual              # 虚拟刚度：被推时让位
θ_cmd = θ_nominal + Δθ           # 带虚拟阻尼与死区
```

被推动时舵机主动让位、松手回弹到原位，即协作机器人 **admittance control** 的极简形式。

必须回答的稳定性问题：虚拟刚度取小为何不自激？
答案：虚拟阻尼 + 一阶低通 + 采样率（1kHz 对 50Hz 舵机带宽有 20 倍余量）+ 死区。

**D3 · 舵机健康监测（选做，成本极低）**

长期记录自由运动段的电流基线，基线随齿轮磨损与积灰缓慢上升。连续运转两周做加速老化，得到一条趋势曲线，超过阈值时提示保养。
这是把工业设备 PHM 的思路用在 5 元舵机上，成本仅为"让它一直转"。

### 5.3 验证项

- [ ] 基线漂移曲线（30 分钟）
- [ ] 力估计误差（砝码 / 弹簧秤标定对照）
- [ ] 让位跟随误差、回位重复精度
- [ ] 误触发率（正常表情动作时的假阳性）
- [ ] 老化趋势曲线（选做）

## 6. 亮点 ②：实时性测量与故障注入

### 6.1 问题

"≤50ms" 目前是一个目标值：没有测量口径、没有分布、没有失效场景。

### 6.2 M1 · 时间契约测量

- 用 DWT 周期计数器打点，明确"延迟"的起止时刻（**口径必须写进文档，否则数字无意义**）
- 每项 ≥100 次采样，输出 **均值 / P50 / P95 / P99 / 抖动**
- 原始数据存 CSV + 分析脚本，任何人 clone 后可复现同一张图

### 6.3 M2 · 故障注入矩阵

| 故障 | 注入方式 | 期望行为 | 通过标准 |
|---|---|---|---|
| 心跳中断 | 拔 UART | 300ms 内卸力、进独立模式 | 不失控 |
| I2C 从机 NACK | 拔 OLED 线 | 不卡死，表情降级为"仅舵机" | 主循环不停 |
| ADC 饱和 | 强制堵转 | 200ms 内卸力报警 | 不烧舵机 |
| UART 位翻转 | 人为改字节 | CRC8 检出并丢弃 | 不误动作 |
| 主循环卡死 | 人为死循环 | 看门狗复位并记录原因 | 能自恢复 |
| 掉电重启 | 拔电源 | 状态从 Flash 恢复 | 不丢配置 |

每一条落成一个可重跑的测试用例。**失效行为比理想性能更能说明系统上过真机**，这也是四项能力里最容易验证、最容易被忽略的一项。

## 8. 设计评审问题

实现前先写下答案。**答不出来的那一项，说明对应的功能还没真正做通。**

| 问题 | 考察点 | 答不上说明 |
|---|---|---|
| 延迟是端到端还是单段？从哪个时刻算起？ | 测量口径严谨性 | 数字没有定义 |
| 200 点采样落在 PWM 周期内的哪个位置？为什么？ | 是否理解电机电流的真实波形 | 只照搬了参考实现 |
| 20KB RAM 的峰值怎么算出来的？ | 是否做过内存规划 | 没在真芯片上跑过 |
| 50ms 是均值还是最坏情况？抖动多少？ | 实时系统基本素养 | 没测过分布 |
| 虚拟刚度调小后为何不自激？ | 控制理论基本功 | 只调参未建模 |
| 被推、负载变化、电压跌落三者如何区分？ | 故障诊断思维 | 只会分类不会判据 |
| 该模型比决策树好多少？值这几 KB 吗？ | 工程判断力 | 保留模型缺乏理由 |
| 断网、断 UART 时系统处于什么状态？ | 降级设计 | 未考虑失效路径 |
| 换一种执行器（无刷 / 步进）这套代码还能用吗？ | 抽象程度 | 逻辑硬编码在具体硬件上 |

## 9. 不做清单

补充 [`04_技术方案.md`](04_技术方案.md) 第 5 节的反噱头清单：

| 不做 | 原因 |
|---|---|

| 继续增加 CI / 流程 / 模板文件 | 治理已收口，边际收益为零（见 [`06`](06_仓库协作规范.md) 第 10.2 节） |
