## 2. 分支模型

个人项目用简化 trunk-based，不引入 develop / release 分支：

```
main ─────●────────────●─────────●────── 始终可交付
           \          / \       /
            ●──●──●──●   ●──●──●          feat/m01-*、feat/p1-* 等短分支
```

| 规则 | 说明 |
|---|---|
| `main` 保护 | 已开启（见第 7 节）：禁 force push / 禁删除；不强制 review，PR 需过文档检查；管理员可绕过，直接 push 不受影响 |
| 分支粒度 | 一个里程碑或一项能力一支，验收清单勾完才合并 |
| 合并方式 | 里程碑用 `--no-ff` 留一个合并点，方便回看；零散修复可快进 |
| 命名 | `feat/m01-oled-face`、`fix/servo-power-dip`、`docs/learning-route` |

> 分支不是为了流程好看，是为了**出问题时能快速回到上一个能跑的版本**。

## 3. 提交规范

格式：`<type>(<scope>): <简述>`，详见 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)。

三条与本项目强相关的约定：

1. **`perf` / 延迟相关提交必须带实测数据**，写进提交正文（均值 / P95 / 抖动），否则视为没做。
2. **代码只有一份**：不搞"实验工程"与"产品工程"两套并存；试验性代码用分支或 tag 隔离，合进 `main` 就必须整理干净。
3. **编译产物不入库**，`.gitignore` 已覆盖 Keil 的 Objects / Listings / `*.uvoptx` 等。

## 5. 标签体系

仓库默认已有 `bug` / `enhancement` / `documentation` 等 10 个标签；以下 16 个自定义标签已由脚本同步：

| 前缀 | 取值 | 用途 |
|---|---|---|
| `stage/` | `P0` `P1` `P2` `P3` `P4` | 归属阶段，用于筛选 |
| `area/` | `firmware` `hardware` `docs` `cognition` `ci` | 归属目录 / 层次 |
| `type/` | `experiment` `benchmark` `refactor` | 实验性质、测量数据、重构 |
| `constraint/` | `realtime` `privacy` `offline` | 涉及硬约束的改动，改动时要格外小心 |

> 标签不是装饰：`constraint/realtime` 一出现，就提醒自己要重新测延迟预算。
> 标签、里程碑的截止日与描述、仓库 description / topics、`main` 分支保护规则都写在 [`../.github/repo-meta.json`](../.github/repo-meta.json)；改配置后跑一次 `--setup` 即可同步，不用逐个手点。

## 6. 验收、tag 与 release

- 每个阶段完成 → 合并到 `main` → 打轻量 tag → 在对应 Issue 里贴延迟数据与演示链接 → 关闭 Issue。
- **只有 P4 才发 Release**；中间阶段不打 release，避免制造"已发布"的错觉。
- tag 命名见第 4 节；里程碑完成记录同步写进 [`03_学习日志.md`](03_学习日志.md)。

## 7. 仓库非代码配置与剩余手动项

**声明式配置**：[`../.github/repo-meta.json`](../.github/repo-meta.json) 是 description / homepage / topics / 标签 / 里程碑 / `main` 分支保护的单一来源。改完执行：

```bash
python scripts/create_issues.py --check-config          # 校验配置结构（CI 同款）
python scripts/create_issues.py --setup --dry-run       # 预览变更，不写入
python scripts/create_issues.py --setup                 # 同步（凭据自动解析，不需要 PAT）
```

凭据按 `GITHUB_TOKEN` → `gh auth token` → `git credential fill` 自动解析；本机实测复用的是 `git push` 的 OAuth 登录态（scopes 含 `repo`），所以只要能推送就能同步。全部操作幂等，重复运行可当配置体检；远端被误改时 `--setup` 会按配置修回。CI 通过 `--check-config` 校验 JSON 结构与脚本语法。

匿名预览只读取公开数据；分支保护端点需要认证，此时仅展示本地目标值，显式设置 `GITHUB_TOKEN` 可获得完整预览。

**`main` 分支保护**（2026-11-15 开启，已纳入 `--setup` 声明式同步）：

| 规则 | 取值 | 原因 |
|---|---|---|
| 禁止 force push / 删除分支 | 开（保护默认自带） | 防不可逆的误操作 |
| 必需状态检查 | `Markdown 相对链接完整性`，strict = false | PR 合并前必须过文档检查；单人项目不必要求分支与 main 同步 |
| 必需 PR 审查 | 关 | 单人项目无人 review，开了会锁住自己 |
| 管理员一并受约束 | 关 | 保留 owner 直接 push；勾上后新提交尚无 CI 结果，会被 `GH006` 拦下 |
| 线性历史 | 关 | 与第 2 节「里程碑用 `--no-ff` 留合并点」冲突 |

检查名来自 [`../.github/workflows/ci.yml`](../.github/workflows/ci.yml) 里 job `docs` 的 `name`。改 job 名时必须同步改 `repo-meta.json` 的 `branch_protection.required_status_checks.contexts`，否则 PR 会一直停在 `Waiting for status to be reported`。**改保护规则请改配置文件后跑一次 `--setup`，不要只在网页上点**——否则下次同步会把网页上的改动覆盖掉。

## 8. 目录与命名约定

固件采用**单一工程 + 三层分层**，不按里程碑并排放多个工程：

| 目录 | 职责 | 硬规则 |
|---|---|---|
| `app/` | 业务逻辑：状态槽、表情参数、力估计、协议编解码 | **禁止 include HAL / CMSIS**，否则无法在 PC 上编译测试 |
| `bsp/` | 板级支持：SSD1306、舵机 PWM、电流采样、串口 | 禁止写业务逻辑 |
| `platform/` | CubeMX 生成 | 禁止手改，要改就改 `.ioc` |
| `tests/` | host 端单元测试 | 只测 `app/`，不测 `bsp/` |
| `tools/` | 上位机、波形分析、数据采集 | Python 为主 |

- 依赖方向单向：`app → bsp → platform`，不可反向、不可跨层
- 学习轨迹用 **git tag**（`learn/gpio`、`learn/pwm`…）+ [`03_学习日志.md`](03_学习日志.md) 承载，不再用目录名记录
- 每个目录**第一次有真实代码时创建**，不提前建空目录（与第 10 节的判断标准一致）

2026-11 已删除原 6 个占位工程目录（`里程碑01_表情脸`、`10_电流触觉`、`90_v1_整合` 等，均只有 README、零代码），理由见 [`../firmware/README.md`](../firmware/README.md) 第 3 节。
**这是重构成本最低的时刻** —— 等写了代码再改，成本翻十倍。

详见 [`../firmware/README.md`](../firmware/README.md)。

### 10.1 Keil 与 Make 双轨怎么不打架

原则：**工程文件不承载逻辑**。

```
firmware/
├── app/             # 业务逻辑，不 include HAL，可被 host 测试
├── bsp/             # 板级驱动，只依赖 HAL
├── platform/        # CubeMX 生成，两边共用
├── Makefile         # CI 用
└── MDK-ARM/         # Keil 工程，只加文件引用，用于下载调试
```

- 逻辑写在 `app/`，**不依赖任何 HAL / CMSIS 头文件** → 能直接在 PC 上编、在 CI 上跑
- `bsp/` 是唯一允许碰寄存器与 HAL 的层
- 新增源文件时两边各加一次引用，这是双轨的唯一成本

### 10.2 明确**不**加的流程

单人项目加这些只会产生噪音，且会稀释"这些文件都有人维护"的可信度：

| 不加 | 原因 |
|---|---|
| `CODE_OF_CONDUCT.md` | 没有社区，写了是模板味 |
| `SECURITY.md` / Dependabot | 无外部依赖需要扫描 |
| 强制 PR review / 双人审批 | 单人仓库，开了会锁死自己（第 7 节已说明） |
| 复杂 release 流水线 | P4 才发版，现在建是空转 |

> **判断标准：一条流程只有在「能拦住一类真实发生过的错误」时才值得存在。**
> 拦不住的流程就是表演，而表演是简历项目最常见的死法。

## 11. 一句话原则

> **能被验证的才叫进度。** 提交、Issue、tag 都只是把「验证过的结果」固定下来，不是 progress 本身。
