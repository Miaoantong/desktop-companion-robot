## 2. 分支模型

个人项目用简化 trunk-based，不引入 develop / release 分支：

```
main ─────●────────────●─────────●────── 始终可交付
           \          / \       /
            ●──●──●──●   ●──●──●          feat/m01-*、feat/p1-* 等短分支
```

| 规则 | 说明 |
|---|---|
| `main` 保护 | 不强制 review，但文档链接检查（CI）必须过 |
| 分支粒度 | 一个里程碑或一项能力一支，验收清单勾完才合并 |
| 合并方式 | 里程碑用 `--no-ff` 留一个合并点，方便回看；零散修复可快进 |
| 命名 | `feat/m01-oled-face`、`fix/servo-power-dip`、`docs/learning-route` |

> 分支不是为了流程好看，是为了**出问题时能快速回到上一个能跑的版本**。

## 3. 提交规范

格式：`<type>(<scope>): <简述>`，详见 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)。

三条与本项目强相关的约定：

1. **`perf` / 延迟相关提交必须带实测数据**，写进提交正文（均值 / P95 / 抖动），否则视为没做。
2. **实验工程可以乱，产品工程必须干净**；`90_v1_整合` 不复制实验代码，只重构。
3. **编译产物不入库**，`.gitignore` 已覆盖 Keil 的 Objects / Listings / `*.uvoptx` 等。

## 5. 标签体系（建议）

仓库默认已有 `bug` / `enhancement` / `documentation`。建议再手动补以下几组：

| 前缀 | 取值 | 用途 |
|---|---|---|
| `stage/` | `P0` `P1` `P2` `P3` `P4` | 归属阶段，用于筛选 |
| `area/` | `firmware` `hardware` `docs` `cognition` `ci` | 归属目录 / 层次 |
| `type/` | `experiment` `benchmark` `refactor` | 实验性质、测量数据、重构 |
| `constraint/` | `realtime` `privacy` `offline` | 涉及硬约束的改动，改动时要格外小心 |

> 标签不是装饰：`constraint/realtime` 一出现，就提醒自己要重新测延迟预算。

## 6. 验收、tag 与 release

- 每个阶段完成 → 合并到 `main` → 打轻量 tag → 在对应 Issue 里贴延迟数据与演示链接 → 关闭 Issue。
- **只有 P4 才发 Release**；中间阶段不打 release，避免制造"已发布"的错觉。
- tag 命名见第 4 节；里程碑完成记录同步写进 [`03_学习日志.md`](03_学习日志.md)。

## 7. 需要手动设置的仓库项

以下项目前无法通过接口代设，建议在 GitHub 仓库页花两分钟补齐：

| 位置 | 建议值 |
|---|---|
| About → Description | `隐私优先、慢脑-快反射架构的桌面陪伴机器人；电流触觉 + 雷达在场感知，默认不采集图像` |
| About → Topics | `stm32` `esp32-s3` `embedded` `companion-robot` `sensorless-force-estimation` `privacy-by-design` `real-time` `desktop-robot` |
| About → Website | 项目演示视频或作品页（P4 后填） |
| Settings → Milestones | 按第 4 节的 5 个阶段建，截止日取各阶段末月 |
| Projects | 建一个看板，列 `待办 / 进行中 / 待验证 / 已完成`，卡片从阶段 Issue 拆出 |
| Issues → Labels | 按第 5 节补齐自定义标签 |
| Settings → Branches | 可选：给 `main` 加保护，要求 CI 通过后才允许合并 |
| GitHub 集成权限 | 创建 Issue 返回 403；App 权限由平台注册决定，重新授权无法补。改用 [`../scripts/create_issues.py`](../scripts/create_issues.py) + 个人 fine-grained PAT，详见 [`../.github/ISSUES/README.md`](../.github/ISSUES/README.md) |

> 描述里**别写"AI 聊天机器人"**——这会把项目的定位讲歪，见 `01_项目规划.md` 的三条判断标准。

## 8. 目录与命名约定

| 编号 | 含义 |
|---|---|
| `里程碑XX_*` | 学习轨迹，跟着外设学习顺序走，允许保留"当时写得很笨"的代码 |
| `10_` `20_` | 产品轨迹里的实验工程，可独立编译、可独立运行 |
| `90_v1_整合` | 最终产品工程，重构实验代码而来，不直接复制 |
| `shared/` | 跨工程共享的协议定义、CRC、时间戳工具；**P2 才写，现在不预留假接口** |

详见 [`../firmware/README.md`](../firmware/README.md)。

## 10. 一句话原则

> **能被验证的才叫进度。** 提交、Issue、tag 都只是把「验证过的结果」固定下来，不是 progress 本身。
