## 2. 分支模型

个人项目用简化 trunk-based，不引入 develop / release 分支：

```
main ─────●────────────●─────────●────── 始终可交付
           \          / \       /
            ●──●──●──●   ●──●──●          feat/m01-*、feat/p1-* 等短分支
```

| 规则 | 说明 |
|---|---|
| `main` 保护 | 已开启（见第 7 节）：禁 force push / 禁删除；不强制 review，PR 需过文档检查；管理员可绕过，直接 push 不受影响 |
| 分支粒度 | 一个里程碑或一项能力一支，验收清单勾完才合并 |
| 合并方式 | 里程碑用 `--no-ff` 留一个合并点，方便回看；零散修复可快进 |
| 命名 | `feat/m01-oled-face`、`fix/servo-power-dip`、`docs/learning-route` |

> 分支不是为了流程好看，是为了**出问题时能快速回到上一个能跑的版本**。

## 3. 提交规范

格式：`<type>(<scope>): <简述>`，详见 [`../CONTRIBUTING.md`](../CONTRIBUTING.md)。

三条与本项目强相关的约定：

1. **`perf` / 延迟相关提交必须带实测数据**，写进提交正文（均值 / P95 / 抖动），否则视为没做。
2. **实验工程可以乱，产品工程必须干净**；`90_v1_整合` 不复制实验代码，只重构。
3. **编译产物不入库**，`.gitignore` 已覆盖 Keil 的 Objects / Listings / `*.uvoptx` 等。

## 5. 标签体系

仓库默认已有 `bug` / `enhancement` / `documentation` 等 10 个标签；以下 16 个自定义标签已由脚本同步：

| 前缀 | 取值 | 用途 |
|---|---|---|
| `stage/` | `P0` `P1` `P2` `P3` `P4` | 归属阶段，用于筛选 |
| `area/` | `firmware` `hardware` `docs` `cognition` `ci` | 归属目录 / 层次 |
| `type/` | `experiment` `benchmark` `refactor` | 实验性质、测量数据、重构 |
| `constraint/` | `realtime` `privacy` `offline` | 涉及硬约束的改动，改动时要格外小心 |

> 标签不是装饰：`constraint/realtime` 一出现，就提醒自己要重新测延迟预算。
> 标签、里程碑的截止日与描述、仓库 description / topics 都写在 [`../.github/repo-meta.json`](../.github/repo-meta.json)；改配置后跑一次 `--setup` 即可同步，不用逐个手点。

## 6. 验收、tag 与 release

- 每个阶段完成 → 合并到 `main` → 打轻量 tag → 在对应 Issue 里贴延迟数据与演示链接 → 关闭 Issue。
- **只有 P4 才发 Release**；中间阶段不打 release，避免制造"已发布"的错觉。
- tag 命名见第 4 节；里程碑完成记录同步写进 [`03_学习日志.md`](03_学习日志.md)。

## 7. 仓库非代码配置与剩余手动项

**声明式配置**：[`../.github/repo-meta.json`](../.github/repo-meta.json) 是 description / homepage / topics / 标签 / 里程碑的单一来源。改完执行：

```bash
python scripts/create_issues.py --setup --dry-run   # 匿名预览变更
python scripts/create_issues.py --setup             # 同步（凭据自动解析，不需要 PAT）
```

凭据按 `GITHUB_TOKEN` → `gh auth token` → `git credential fill` 自动解析；本机实测复用的是 `git push` 的 OAuth 登录态（scopes 含 `repo`），所以只要能推送就能同步。全部操作幂等，重复运行可当配置体检；CI 会校验该 JSON 的合法性。

| 位置 | 状态 / 说明 |
|---|---|
| About → Description | **已同步**：`隐私优先、慢脑-快反射架构的桌面陪伴机器人；电流触觉 + 雷达在场感知，默认不采集图像` |
| About → Topics | **已同步**：8 个，值见配置文件 |
| About → Website | 留空，P4 有演示视频后在配置里填 `homepage` |
| Issues → Labels | **已同步**：16 个自定义标签（默认 10 个保留） |
| Settings → Milestones | **已同步**：5 个阶段里程碑，截止日见配置文件 |
| 阶段 Issue #1–#5 | **已挂载**：`stage/P?` 标签 + 对应里程碑 |
| Settings → Branches | **已开启**，配置明细见本节末尾 |
| Projects | 仍需手动：看板列 `待办 / 进行中 / 待验证 / 已完成`，卡片从阶段 Issue 拆出 |
| GitHub 集成权限 | App 的 Issues 写权限由平台注册决定，重新授权补不了；已改用本机凭据 + [`../scripts/create_issues.py`](../scripts/create_issues.py)，详见 [`../.github/ISSUES/README.md`](../.github/ISSUES/README.md) |

> 描述里**别写"AI 聊天机器人"**——这会把项目的定位讲歪，见 `01_项目规划.md` 的三条判断标准。

**`main` 分支保护**（2026-11-15 经 REST API 开启；这一项不在 `--setup` 的同步范围内）：

| 规则 | 取值 | 原因 |
|---|---|---|
| 禁止 force push / 删除分支 | 开（保护默认自带） | 防不可逆的误操作 |
| 必需状态检查 | `Markdown 相对链接完整性`，strict = false | PR 合并前必须过文档检查；单人项目不必要求分支与 main 同步 |
| 必需 PR 审查 | 关 | 单人项目无人 review，开了会锁住自己 |
| 管理员一并受约束 | 关 | 保留 owner 直接 push；勾上后新提交尚无 CI 结果，会被 `GH006` 拦下 |
| 线性历史 | 关 | 与第 2 节「里程碑用 `--no-ff` 留合并点」冲突 |

检查名来自 [`../.github/workflows/ci.yml`](../.github/workflows/ci.yml) 里 job `docs` 的 `name`。改 job 名时必须同步改这里的必需检查，否则 PR 会一直停在 `Waiting for status to be reported`。

## 8. 目录与命名约定

| 编号 | 含义 |
|---|---|
| `里程碑XX_*` | 学习轨迹，跟着外设学习顺序走，允许保留"当时写得很笨"的代码 |
| `10_` `20_` | 产品轨迹里的实验工程，可独立编译、可独立运行 |
| `90_v1_整合` | 最终产品工程，重构实验代码而来，不直接复制 |
| `shared/` | 跨工程共享的协议定义、CRC、时间戳工具；**P2 才写，现在不预留假接口** |

详见 [`../firmware/README.md`](../firmware/README.md)。

## 10. 一句话原则
