## 1. 目标结构

```
firmware/
├── app/            # 业务逻辑：表达式参数、力估计、状态槽、协议编解码  ← 已有 protocol/
├── bsp/            # 板级支持：SSD1306、舵机 PWM、电流采样、串口      ← C1
├── platform/       # CubeMX 生成（Core / Drivers / 启动文件），不手改   ← C1
├── tests/          # host 端单元测试：gcc 直接编，不需要板子            ← 已有
├── tools/          # 上位机、波形分析、数据采集脚本                     ← C3
├── Makefile        # make test：与 CI 完全同一条命令                    ← 已有
└── README.md       # 本文件
```

每个目录在第一次有真实代码时创建，**不提前建空目录**。

## 2. 三层依赖规则（这个文件里唯一必须记住的事）

```
app  →  bsp  →  platform
```

依赖只能向右，不能反向，不能跨层。

| 层 | 允许 | **禁止** |
|---|---|---|
| `app/` | 纯 C 算法、状态机、协议帧编解码、滤波 | **禁止 include 任何 HAL / CMSIS 头文件**；禁止直接读写寄存器 |
| `bsp/` | 调用 HAL、配外设、提供 `servo_set_angle()`、`adc_read_current()` 这类原子操作 | 禁止写业务逻辑（不许在这里判断"这是轻拍还是重按"） |
| `platform/` | CubeMX 生成 | 禁止手改；要改就改 `.ioc` 重新生成 |

**为什么必须这样分**：

`app/` 不依赖 HAL，才能在 PC 上编译、才能跑单元测试、才能进 CI。
硬件在环难自动化，但**逻辑可以** —— 这是嵌入式项目能拥有真正测试的唯一办法。

## 3. 为什么废弃「里程碑XX_」目录

原方案并排放 6 个独立工程（`里程碑01_表情脸`、`10_电流触觉`、`90_v1_整合`…），已全部删除，原因：

| 问题 | 说明 |
|---|---|
| 重复配置 | 6 份 CubeMX 配置，改一个引脚要改 6 处，必然不同步 |
| 无信息量 | 6 个只有 README 的目录不承载任何代码事实，读者无法据此判断进度 |
| 掩盖问题 | "实验工程可以乱，产品工程要重构"听起来合理，实际是给自己留了不整理代码的借口 |

学习轨迹的正确载体是 **git tag + 学习日志**：每学完一个外设打一个 tag，代码继续演进，历史随时可回看。

## 4. 构建与测试

clone 下来一条命令就能验证，不需要打开 Keil：

```bash
make test      # 编译 app/ 层并运行 host 端单元测试（秒级）
make clean
```

当前输出（63 项断言）：

```
[ RUN  ] suite_crc8
[  OK  ] suite_crc8
[ RUN  ] suite_frame
[  OK  ] suite_frame

63 checks, 0 failure(s)
RESULT: PASS
```

- 交叉编译（`.elf` + size 报告）等 `platform/` 由 CubeMX 生成后再加 target。
  **不写空壳配方**：一个跑不通的 target 比缺失 target 更容易掩盖问题
- Keil 保留，仅用于下载、断点调试
- CI 跑 `make test`，并额外 `grep` 检查 `app/` 没有 include HAL / CMSIS

### 测试里两条值得记住的结论

**① 只有"已知校验值"能抓住错的多项式。**
CRC-8/ATM 对 `"123456789"` 必须是 `0xF4`。做过一次变异检验：把多项式从 `0x07` 改成 `0x1D`，
`suite_crc8` 立刻红，但 `suite_frame` 全绿——因为编解码用的是同一个错多项式，
roundtrip 依然自洽。**回环测试证明不了正确性，只证明自洽。**

**② 逐字节状态机必须配"字节间超时复位"。**
半截帧之后若不复位，下一帧的 `0xAA 0x55` 会被当成 TYPE/LEN 吃掉，症状是"偶发丢一整帧"。
`frame_parser_reset()` 用于复位；`tests/test_frame.c` 中有一条用例把该**限制**固化为断言，
以免后续误认为解析器已覆盖该场景。

## 5. 第一个模块：`app/protocol/`

| 文件 | 内容 | 关键决定 |
|---|---|---|
| `crc8.h/.c` | CRC-8/ATM（poly 0x07, init 0x00） | 逐位算、不查表：帧 ≤ 37 字节，不到 10µs，256 字节表在 20KB RAM 里不划算 |
| `frame.h/.c` | 定长帧编解码 + 逐字节解析状态机 | 双字节 SOF `AA 55`、LEN ≤ 32、CRC 失败静默丢帧 |

线格式：

```
+------+------+-------+------+-------------+-------+
| 0xAA | 0x55 | TYPE  | LEN  | PAYLOAD[N]  | CRC8  |
+------+------+-------+------+-------------+-------+
                     |<---- CRC 覆盖范围 ---->|
```

为什么从这里开始，而不是从点灯开始：**协议是 L0 与 L1 的唯一契约，也是唯一能在没有硬件时写对的东西。**
它不依赖 HAL，所以能进 CI；它会被电流采样、心跳、命令三条链路复用，所以先写它，
后面每加一个功能都是在已验证的地基上加。

`frame_parser_t` ≈ 44 字节，静态分配，无动态内存——这一点在 C5 部署 int8 模型时会变成硬约束。

- 新增源文件时，`Makefile` 与 `MDK-ARM/*.uvprojx` 各加一次引用（双轨的唯一成本）
